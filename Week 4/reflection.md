I build a book_appointment() function and a display_appointments() function, storing everything in a simple list of dictionaries with patient name, practitioner name, and appointment time. I'd also gone through the case study first and worked out what data I actually needed to store and what was still unclear.
 I knew something wasn't right about how appointment times were being stored as plain strings, but AI put it into clearer terms. It explained that no real date/time object, no unique IDs, no duplicate check. It became easier to prioritise what to fix. It also showed me a different way of structuring the same logic, splitting things into smaller functions.
AI did make assumptions, though, and it didn't flag them as assumptions. It just wrote the code as if blank names, None values, and duplicate bookings were all fine. There was no validation at all in the AI version. It looked clean and well-organised, but that cleanness was hiding the fact that it was less careful than my own version, which happened to catch some bad input almost by accident.
The only way I actually found that out was by running both versions through the same test cases. A normal booking, a blank name, a duplicate slot, and None values then comparing the real output line by line. I didn't just read the AI code and trust it looked fine; I had to execute it to see it fail the blank name and None value tests. That was the real verification step, not the code review.
What was left for me to do after that was the actual engineering judgement: deciding which one improvement was worth making given everything that was broken, since the brief asked for exactly one controlled change rather than fixing everything at once. I picked the duplicate-booking check because it's the specific problem the clinic actually complained about in the case study. Then I wrote it, wired it into the existing function, and re-tested. Normal booking, a second distinct booking, the duplicate itself getting blocked, and a same practitioner different time case.
